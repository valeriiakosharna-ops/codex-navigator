Module 5 · Governance, safety and enterprise rollout

Coordinating Codex across teams and systems

Split a large change into workstreams, give each one a verification contract (the evidence it must produce and what happens if it fails), and bring parallel outputs back together safely.

For technical specialists⏱ ~55 minGraded · 4 pt

Why this matters#

One developer with one agent is easy to keep on track. Five teams, each running several agents on one platform migration, is a different problem. The work rarely fails inside a workstream. It fails at integration: two streams changed the same interface differently, one stream's "done" meant "compiles", and nobody can tell which output can be trusted.

The Scale Codex Across Teams and Systems path is about exactly this: dividing complex work into workstreams your team can verify and bring back together.

Split the change into workstreams#

A good split has workstreams that are independent to build and cheap to integrate: the boundaries between them are interfaces that are agreed before anyone starts.

Splitting a migration
✗ Vague
Team A does the backend, team B the frontend, team C the rest. Everyone uses Codex.

The boundaries are org-chart lines, not interfaces. Nobody owns "the rest", and integration is left to luck.

✓ Specific
Interface first: the new Orders API schema (orders.v2.yaml) is frozen by the platform team.
WS1 Orders service implements v2 behind a flag. Owner: Platform. Writes: services/orders/
WS2 Web checkout consumes v2 via the generated client. Owner: Web. Writes: web/checkout/
WS3 Data migration script + dry run on a copy. Owner: Data. Writes: tools/migrate/
Integration: Platform lead merges in order WS1 → WS3 → WS2, behind the flag.

A frozen interface, one owner and one write area per stream, and an explicit order of integration.

A verification contract for each workstream#

The contract answers three questions before the work starts. What evidence must this stream produce? Who checks it? What happens if a check fails?

Use case
Verification contract for a workstream
Tech lead coordinating a migration

Situation

Three workstreams run in parallel with Codex. Last time, "done" from one team meant "unit tests pass", and the integration broke in staging.

Prompt

For workstream WS3 (data migration), draft a verification contract:
- required evidence: dry-run report on a production-size copy (row counts before/after,
  checksums per table, duration), rollback tested, idempotency test output;
- who verifies it and how;
- failure handling: what blocks integration, what can ship behind the flag;
- what the stream must NOT change (other streams' write areas, the frozen schema).
Save it as docs/migration/ws3-contract.md for review.

Good outcome

A one-page contract the stream's agents and people work against. Integration accepts evidence, not assurances.

Tips

  • Put the contract in the repo and reference it from AGENTS.md in that stream's folder, so every Codex session sees it.
  • "Done" = the evidence in the contract exists and has been checked. Nothing less.
