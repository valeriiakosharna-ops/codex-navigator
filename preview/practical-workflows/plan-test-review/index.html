Module 3 · Core agentic capabilities

Closed-loop testing and debugging

Let Codex run builds, linters and tests, read the failures and fix its own work, locally and in the cloud, and recognise when "tests pass" proves nothing.

For technical specialists⏱ ~50 minGraded · 5 pt

Why this matters#

An agent can write a lot of code quickly, so the bottleneck moves to verification. Codex closes the loop itself: it runs the build, linters and tests, reads the stack trace, changes the code and runs everything again until it passes. That loop is only as good as two things you control. First, the environment has to be able to run the checks at all. Second, passing the checks has to actually mean the code works.

Debugging with Codex#

Use case
A flaky test
Backend developer

Situation

test_checkout_total fails about once in ten CI runs. Nobody can reproduce it locally.

Prompt

Investigate why tests/test_checkout.py::test_total fails intermittently.
1) Reproduce it first: run it 50 times and report the failure rate.
2) Find the root cause. Show the evidence (stack traces, timing, shared state).
3) Fix the cause, not the symptom. Do not change the assertion or add retries.
Done when 50 consecutive runs pass, and you list what you did NOT verify.

Good outcome

A reproduction, a root-cause explanation backed by evidence, a minimal fix and the loop output.

Tips

  • Ask for the reproduction before the fix. A fix for a bug nobody reproduced is a guess.
  • "Do not change the assertion" blocks the most common fake fix.

When "tests pass" means nothing#

Fake green

An agent told to "make the tests pass" can do it the wrong way. It can change the assertion to match the bug, skip or delete the failing test, mock away the code under test, or catch and swallow the exception. Always read the test diff as carefully as the code diff. The lab in this module trains exactly this.

Asking for a fix
✗ Vague
The tests are red. Make them pass.

Every fake fix in the warning above satisfies this prompt.

✓ Specific
The discount tests fail after yesterday's change. Find out why.
Fix the production code; don't modify, skip or delete tests unless you
explain why the test itself is wrong and I approve it.
Done when the full suite passes; report the commands and output.

The constraint closes off the shortcuts, and any change to a test needs your approval.
