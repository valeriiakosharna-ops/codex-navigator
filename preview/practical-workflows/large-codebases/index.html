Module 3 · Core agentic capabilities

Navigating and refactoring large codebases

Map the relevant part of a big repository, trace dependencies, plan a bounded refactor and carry it out in reviewable steps, keeping the architectural context where Codex and your team can find it.

👥 For: Technical⏱ ~60 minGraded · 4 pt

Why this matters#

In a small repo, Codex can read everything. In a large one it can't, and neither can you. Large refactors fail in two familiar ways. The agent changes far more than you asked for, or it changes the right files but breaks a caller three directories away that nobody mentioned.

The fix is the same as for a human team: map first, plan a bounded slice, execute in reviewable steps, and write the context down so it survives the next session.

Step 1: map before you change#

Start read-only. Ask for a map of the part you care about, with file references you can check:

Use case
Mapping a payments module before a refactor
Backend developer

Situation

You need to replace a hand-rolled currency type with the shared Money library across the billing code. Nobody knows how far the old type spreads.

Prompt

Read-only task, don't edit anything.
Map every use of `LegacyAmount` in this repo: which modules create it, which only pass it
through, which serialise it (DB, API, queues). Group the call sites by module, with file:line.
List public APIs and stored formats that would change if the type changed.
Finish with the 3 riskiest places and why.

Good outcome

A dependency map with file references, grouped by module, including the serialisation boundaries that make the refactor risky.

Tips

  • "Don't edit anything" (or read-only mode) makes exploration safe.
  • Save the map to a file in the repo (for example docs/refactor-money/map.md) so the next session and your reviewers can use it.

Step 2: plan a bounded slice#

A good refactor plan names what's in scope, what isn't, the order of steps, and how each step is verified. That's what the cookbook's ExecPlan is. Put it in the repo, not only in the chat.

Asking for the refactor
✗ Vague
Migrate billing to the Money library.

An unbounded change touching dozens of files, with no order of steps, no stopping points and no definition of done. The result is one giant diff nobody can review.

✓ Specific
Using docs/refactor-money/map.md, write an ExecPlan in docs/refactor-money/plan.md:
scope = the invoices module only; out of scope = API and DB formats.
Split it into steps that each leave the build green and can be reviewed separately.
For each step: files, verification command, rollback.
Stop after writing the plan and wait for my review.

A bounded scope, steps that keep the build green, and a check for each one. The plan is a file the team can review and Codex can follow.

Step 3: execute in reviewable steps, with goals#

For multi-step work, give Codex a goal it can verify itself against.

Where the architectural context lives
  • In the task brief: scope, out-of-scope, constraints. These change per task.
  • In the repo docs (plan, map, ADRs): decisions and findings that should outlive the chat.
  • In AGENTS.md: durable rules for every task, such as "never change public API types without an ADR". Module 4 covers it.
