Module 3 · Core agentic capabilities

Code review and security scans

Use Codex to review pull requests and local changes, then the Codex Security plugin to catch vulnerabilities before production, and read the results critically, without blind trust.

👥 For: Everyone⏱ ~60 minGraded · 4 pt

Why this matters#

When an agent writes code faster than people can read it, review becomes the bottleneck. Codex helps on both sides. It can review a pull request, a branch or your uncommitted changes, and Codex Security goes looking specifically for vulnerabilities such as injection, broken access checks or leaked resources.

This topic is for everyone. Developers run the reviews and scans. PMs, leads and QA need to know what a review or a "no findings" report does and doesn't prove.

Make the reviewer know your rules

Use case
Second pair of eyes before a PR
Developer

Situation

You've finished a feature branch with Codex's help. Before you ask a colleague to review, you want the obvious issues gone.

Prompt

Review my branch against main. Focus on: behaviour changes not mentioned in the
PR description, missing tests for new branches of logic, error handling,
and anything that touches authentication or personal data.
Report findings by severity with file:line. Don't change any code.

Good outcome

A prioritised list of findings with locations. You fix the real ones before a human spends time on the PR.

Tips

  • Keep the review read-only, then fix in a separate step so you can see what changed and why.
  • Your colleague still reviews. Codex removes the noise so they can focus on design and intent.

Codex Security plugin quickstart
Officialdocs⏱ 15 minintermediate

Install the Codex Security plugin in the desktop app or CLI, run a standard read-only scan of a local repository, and review the findings. Your source isn't changed. The scan saves a report with evidence and remediation guidance.

While you study, pay attention to

  • Interpret the result: check the target and revision first, then which areas were reviewed and which were deferred.
  • "A review that reports no findings hasn't necessarily ruled out every vulnerability." Remember this sentence.
  • What the scan creates: report.md for people; findings.json and coverage.json for tools.
  • In a managed workspace the plugin may show "Disabled by admin". That's a policy decision, not a bug.

Reading findings without blind trust#

Two opposite mistakes

Trusting "no findings": the docs say coverage can have gaps, and some areas get deferred. Trusting every finding: each one comes with source evidence, the attacker's prerequisites, how it was validated and what remains uncertain. Use that to decide whether it really applies to your system before anyone spends a day fixing it.
