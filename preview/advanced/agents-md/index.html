What to put in AGENTS.md#

The best practices guide recommends a short and accurate file covering:

  • repository layout (where things live);
  • how to run the project, and the exact build / test / lint commands;
  • engineering conventions and PR expectations;
  • constraints and "do-not" rules;
  • how to verify that work is done.

In the CLI, /init generates a starter AGENTS.md. Treat it as a draft and edit it.

Use case
Writing your team's first AGENTS.md
Developer on a team of six

Situation

Codex keeps running npm test (the whole suite, 9 minutes) and forgets the lint step.

Prompt

Run /init, then edit the generated AGENTS.md so it says:
- use pnpm, never npm;
- for a quick check run `pnpm test --filter <package>`; full suite only before a PR;
- always run `pnpm lint` before declaring the task done;
- never edit files under db/migrations/ — propose a new migration instead.
Keep it under 40 lines.

Good outcome

A short AGENTS.md checked into the repo. Every teammate's Codex now follows the same rules.

Tips

  • When Codex repeats a mistake, ask it to review what went wrong and propose an AGENTS.md update.
  • Link longer docs from AGENTS.md instead of pasting them in.
Best practice

Durable rules go in AGENTS.md (or skills, later). One-off details go in the prompt. Mixing these up is one of the common mistakes the official guide lists.

Configuration layers#

Layer File Use for
Personal defaults ~/.codex/config.toml Your preferred model, effort, approvals
Project .codex/config.toml in the repo Settings the team shares for this project (loaded only if you trust the project)
Profile --profile name Switching between setups, e.g. a careful "review" profile
One-off -c key=value / --config Trying something for a single run (highest precedence)

Review rules in AGENTS.md#

Code review by Codex reads a ## Code Review Rules section from the AGENTS.md closest to the code it governs. Put repository-wide checks at the root and service-specific ones in nested files. The docs advise keeping each rule short, explaining what to flag and the safe path, and leaving formatting and lint to CI.

A review rule
✗ Vague
- Be careful with SQL.

Nobody, human or agent, can act on this. What exactly should be flagged?

✓ Specific
## Code Review Rules
### Database access
- Flag SQL built with string concatenation or f-strings.
  Safe path: parameterised queries via db.query(sql, params).

Says what to flag and what to do instead, and it sits next to the code it governs.

Rules: which commands may leave the sandbox#

AGENTS.md is guidance. Rules are enforcement. A .rules file under ~/.codex/rules/ (or next to any active config layer) matches command prefixes and decides what happens when Codex wants to run that command outside the sandbox: allow, prompt or forbidden. When several rules match, the strictest one wins. Rules are marked experimental in the docs.

# ~/.codex/rules/default.rules
prefix_rule(
    pattern = ["gh", "pr", "view"],
    decision = "prompt",
    justification = "Viewing PRs needs network; confirm first.",
)
prefix_rule(
    pattern = ["git", "push"],
    decision = "forbidden",
    justification = "Never push from an agent session. Open a PR from your own terminal.",
)
