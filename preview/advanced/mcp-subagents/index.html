Module 4 · Advanced configuration and extensibility

MCP and subagents

Connect Codex to databases, APIs and company tools through the Model Context Protocol, and split parallel work across subagents and custom agents, keeping their outputs reviewable.

For technical specialists⏱ ~55 minGraded · 4 pt

Why this matters#

Sooner or later the context Codex needs isn't in the repository. It's in a ticket, a dashboard, a database or internal docs. MCP (Model Context Protocol) is the standard way to plug those in, so you stop copy-pasting.

And sooner or later a task is too wide for one thread: review a PR from six angles, or explore four services at once. Subagents run those parts in parallel and bring the results back to one chat.

Both add power and both add risk: more tools the agent can call, more work happening at once. This topic covers how to use them without losing track.

MCP: bring outside context in#

OpenAI Docs
Model Context Protocol
Officialdocs⏱ 20 minadvanced

How to connect Codex to an MCP server in the desktop app, CLI and IDE (they share one config), and how to build an MCP plugin for your own system.

While you study, pay attention to

  • Two kinds of server: STDIO (a local process started by a command) and Streamable HTTP (a URL, with a bearer token or OAuth).
  • Adding one: codex mcp add <name> -- <command>, Settings → MCP servers in the app or IDE, or [mcp_servers.<name>] in config.toml. /mcp shows what's connected.
  • enabled_tools / disabled_tools: expose only the tools the agent actually needs.
  • ChatGPT on the web doesn't read your local Codex config. There, MCP tools come in through plugins.
Open the material 
# ~/.codex/config.toml (or .codex/config.toml in a trusted project)
[mcp_servers.docs]
command = "npx"
args = ["-y", "@upstash/context7-mcp"]

[mcp_servers.tracker]
url = "https://mcp.example.internal/mcp"
enabled_tools = ["search_issues", "get_issue"]   # read-only tools only
An MCP server is a new door

Every tool a server exposes is something the agent can call, and everything it returns is untrusted input that may carry injected instructions. Start with read-only tools, use enabled_tools to allow only what you need, and let your admin know before you connect company systems. Admins can restrict which servers are allowed (module 5).

Use case
Debugging with production context
Backend developer on call

Situation

An alert fires for checkout errors. The stack trace is in your error tracker, the deploy history in GitHub, and the runbook in the internal wiki.

Prompt

Using the error-tracker and wiki MCP tools (read-only):
pull the last 50 events for CHECKOUT-500, group them by stack trace,
match them to deploys in the last 24 h, and find the runbook section for this error.
Propose the most likely cause with evidence. Don't change any code yet.

Good outcome

A short incident brief that links events, the suspect deploy and the runbook, before anyone opens an editor.

Tips

  • The best practices guide suggests starting with one or two MCP tools that remove a frequent manual step.
  • Keep it read-only while investigating. Fix in a separate, reviewed change.

Subagents: split parallel work#

OpenAI Docs
Subagents
Officialdocs⏱ 20 minadvanced

How Codex spawns specialised agents in parallel and combines their results, and how to define custom agents with their own model and instructions.

While you study, pay attention to

  • Local Codex spawns subagents when you ask directly, or when AGENTS.md or a skill says to. With Ultra, it may delegate on its own.
  • Each subagent does its own model and tool work, so more tokens than a single-agent run.
  • Subagents inherit your sandbox policy. Parallel doesn't mean less safe.
  • Built-in agents: default, worker (implementation), explorer (read-heavy exploration). Custom ones go in ~/.codex/agents/ or .codex/agents/ as TOML files with name, description and developer_instructions.
  • /subagents in the CLI shows the running threads and lets you switch between them.

Asking for a parallel review
✗ Vague
Review this PR thoroughly using lots of agents.

No division of the work, so the agents overlap and the summary is a blur.

✓ Specific
Review this branch against main. Spawn one agent per point, wait for all,
then summarise each point separately with file:line evidence:
1. Security  2. Bugs  3. Race conditions  4. Test flakiness  5. Maintainability
Agents are read-only; don't change any files.

Independent, non-overlapping parts, a combined result that keeps them apart, and no writes. This mirrors the example in the docs.

# .codex/agents/test-auditor.toml  (a project-scoped custom agent)
name = "test-auditor"
description = "Reviews test changes for weakened assertions, skips and over-mocking."
developer_instructions = """
Read-only. For every changed test, report whether it still checks the original behaviour.
Flag changed expected values, skipped tests and mocks of the code under test.
"""
model_reasoning_effort = "high"
When parallel helps, and when it doesn't

Subagents shine when the parts are independent: separate review angles, separate services, separate hypotheses. They hurt when two of them write to the same files. Give each writer its own worktree, or keep the writers in sequence. Module 5 covers coordinating whole teams this way.
