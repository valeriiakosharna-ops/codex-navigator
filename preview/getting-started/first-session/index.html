The Codex CLI, sandbox and approvals

Install and sign in to the CLI, choose a sandbox and an approval policy for a repository task, and check that the boundary really holds.

For technical specialists⏱ ~45 minGraded · 6 pt

Why this matters#

The first hour with an agent shapes your habits. Two things decide whether that hour goes well. The first is a clean starting point, a Git repo you can diff and revert. The second is the right permissions: what Codex may do without asking you. Get both right and you can let Codex move fast without worrying.

Install and sign in#

The docs give a standalone installer for each OS. The npm package works anywhere Node.js runs:

# official installer (macOS / Linux)
curl -fsSL https://chatgpt.com/codex/install.sh | sh

# Windows (PowerShell)
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"

# or with npm, on any OS
npm install -g @openai/codex

Then open a project folder and run codex. On first run, choose Sign in with ChatGPT. On Windows, Codex uses the native Windows sandbox in PowerShell and the Linux sandbox in WSL2. On Linux, install bubblewrap first (see the Sandbox page).

Sandbox and approvals: two separate dials#

  • Sandbox mode decides what Codex can touch: read-only, workspace-write (edit inside the project) or danger-full-access (no sandbox).
  • Approval policy decides when Codex must ask you: on-request (it asks before going outside the sandbox, e.g. network access or files outside the workspace) or never.

For a version-controlled project the docs recommend Auto, which is workspace-write + on-request. For folders without Git they recommend read-only. Network access is off by default.

Even in workspace-write, some paths inside the project stay read-only: .git, .codex, .agents and .aws. The agent can't rewrite your Git history or its own configuration without asking.

Common pitfall

Turning on full access "just to stop the prompts" on day one. The prompts tell you what the agent wants to do. Learn the workflow first, then loosen permissions per trusted repo.

Caution

Treat web content the agent reads as untrusted. Prompt injection can make an agent follow instructions hidden in a page.

Prove the boundary holds#

The unit's goal isn't only to pick permissions. It's to check that they stop work outside the boundary. In a scratch repository, try this once:

  1. Start codex with the default (Auto) and run /status. Note the writable roots.
  2. Ask: "Create notes.txt in the parent folder of this repo." Codex should stop and ask for approval. Decline it.
  3. Ask: "Run curl -I https://example.com in the terminal." Command network access is off by default, so it should ask or fail. It must not quietly succeed. (Codex's separate web-search tool is configured on its own, so test with a command.)
  4. Restart with codex --sandbox read-only and ask it to fix a typo. It can read and propose, but it must ask before writing.

If any step goes through without a prompt, your config (or a profile you forgot about) is looser than you think. Check ~/.codex/config.toml.
