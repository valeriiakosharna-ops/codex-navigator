Giving Codex context and completion criteria

Brief the agent like a new colleague: goal, context, constraints, done-when. Then plan, steer, and ask for the evidence a reviewer needs.

For everyone⏱ ~50 minGraded · 6 pt

Why this matters#

Codex copes with imperfect prompts, but on large repos and high-stakes changes the quality of your request decides the quality of the result. A good request reads like a ticket you'd hand to a capable colleague who joined yesterday.

The four elements#

  1. Goal: what you're changing or building.
  2. Context: the relevant files, docs, examples or error messages. You can @-mention files.
  3. Constraints: standards, architecture, safety rules or conventions to respect.
  4. Done when: a finish line Codex can check itself, such as tests passing or a bug that no longer reproduces.
Same task, two prompts
✗ Vague
make the export faster

No context, no constraints, no finish line. Codex has to guess what "faster" means and where to look.

✓ Specific
Goal: speed up CSV export in src/reports/export.py (export_orders).
Context: exporting 50k orders takes ~40 s; profiling output is in docs/profile.txt.
Constraints: keep the CSV format byte-identical; no new dependencies.
Done when: tests/test_export.py passes and the benchmark script
scripts/bench_export.py reports under 10 s.

Every element is there, and "done when" lets Codex verify its own work.

In the Academy lab

The hands-on lab in Get Started with Codex asks you to give Codex "the right repository context" and "completion criteria". Write those four headings into your first lab prompt. The finish line is the part people skip most.

Plan first for difficult tasks#

For anything multi-step or ambiguous, ask for a plan before code. Switch to plan mode (/plan or Shift+Tab), or ask Codex to interview you until the task is concrete. Approve the plan, then let it build.

Use case
Turning a fuzzy idea into a plan
Tech lead

Situation

Product asks for "audit logging" with no spec.

Prompt

I need audit logging for admin actions in this service. Before writing
any code, interview me: ask up to 8 questions about scope, storage,
retention and privacy. Then propose a step-by-step plan with the files
you would touch. Wait for my approval.

Good outcome

A short Q&A, then a concrete plan you can edit, all before any code is written.

Tips

  • Planning is cheap. Rewriting a wrong implementation is not.
  • Save long plans to a file (the guide suggests a PLANS.md template) so you can continue later.

Steer while it works#

You don't have to wait for a run to finish to correct it. The Prompting docs describe two moves:

  • Steer adds your message to the current run: a change of direction, a missing detail, new information.
  • Queue saves the message for the next run: a follow-up that should wait until this work is done.

For long tasks, /goal turns the prompt into an explicit goal (outcome, constraints, verification) that you can pause, edit or clear while it runs. Module 3 uses it on a large refactor.

Ask for evidence, not reassurance#

"Done" from an agent is a claim. The official path calls the cure evidence a reviewer can check. End every non-trivial task by asking for it:

Closing a task
✗ Vague
Looks good? Then we're done.

You get "Yes, all done!" whether or not anything was verified.

✓ Specific
Before you finish, report:
- which commands you ran and their results (tests, lint, build);
- what you did NOT verify and why;
- files changed, with one line on each;
- any assumption you made that I should confirm.

The reviewer can check the claims in minutes, and the gaps are stated, not hidden.
